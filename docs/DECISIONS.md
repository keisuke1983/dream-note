# DECISIONS.md

重要な設計判断を記録する場所です。
大きな仕様変更や技術判断を行った場合は、日付・判断・理由・影響を追記してください。

## 2026-07-23: DreamとTaskを分ける

判断:

Dreamは夢・人生設計、Taskは現在の行動整理として分ける。

理由:

単なるToDoアプリにすると、長期的な夢とのつながりが失われるため。
一方で、夢だけを扱うと日々の行動に落ちないため、両方を分けつつ関連付ける。

影響:

- `dreams`
- `goals`
- `tasks`

を別テーブルとして扱う。

## 2026-07-23: 今日やることの件数を固定しない

判断:

ホームの「今日やること」は3件固定にしない。

理由:

3件以上やるべき日もあるため。
固定件数にすると、重要な行動が隠れる可能性がある。

現在の実装:

未完了タスクのうち、重要・緊急・期限が近いものを抽出して表示する。

影響:

将来AIが提案する場合も、「3件固定」ではなく、必要数と優先順位を提案する方針にする。

## 2026-07-23: 今日やることは期限順だけで決めない

判断:

「今日やること」は、単に期限が近いタスクの一覧ではなく、夢の実現につながる重要行動を含める。
特に「緊急ではないが重要」な行動を後回しにしない設計を目指す。

理由:

緊急タスクだけで一日が埋まると、長期的な夢や目標に向けた行動が進まないため。
このアプリはToDo消化ではなく、夢を実現するために今日動くことを支援するアプリである。

考慮する要素:

- 緊急性
- 重要性
- 期限
- 関連する夢・目標
- 夢の実現への寄与度
- 最近その夢に向けた行動ができているか

影響:

現在のルールベース実装は重要・緊急・期限3日以内が中心であり、夢への寄与度や最近の行動有無は未実装。
今後、今日やることの抽出ルールやAI提案を設計する際は、この判断を優先する。

## 2026-07-23: Phase 1はAIなしで成立させる

理由:

まず毎日使える基本体験を確認するため。

影響:

AI夢整理画面は準備中表示に留める。

AIプロダクト責任者を中心に、必要な場合だけProduct AI、UX AI、Engineer AI、QA AIの視点を使う。

## 2026-07-23: Groq構造化出力はアプリ側で正規化する

判断:

Groqには厳格すぎないJSON Schemaを渡し、返ってきたJSONをアプリ側で既存Schema互換へ正規化してから検証する。
JSON解析またはSchema検証に失敗した場合のみ、同じユーザー操作内で最大1回だけ再生成する。

理由:

Groq無料枠の `openai/gpt-oss-20b` は正常時の提案品質は実用範囲だが、厳格Schemaだけに依存すると配列件数やSchema適合で不安定になる場合があるため。
無条件リトライでは無料枠を浪費するため、形式異常時だけに限定する。

影響:

- OpenAIとGeminiの実装は残し、Provider切替可能な構造を維持する
- Groqのみ寛容Schemaを使う
- `milestones` が不足した場合は、AI提案表示前に最小限の補完を行う
- AI提案は正式データへ自動保存しないため、既存の夢・目標・タスクは壊れない

また、朝のホーム画面ではまず既存のルールベース今日候補を即時表示し、AIは必要な時だけ優先順と理由を補助する役割にする方が、情報量と待ち時間を抑えられるため。

影響:

- 既存のルールベース「今日やること」は維持する
- AIは既存タスクの推薦順と理由だけを返す
- AIはタスクを勝手に追加、変更、削除、完了しない
- `today_ai_suggestions` テーブルを追加する
- 今日やることAI履歴一覧は今回実装しない

## 2026-07-24: 週次レビューAIは事実集計を先に行う

判断:

週次レビューAIは、完了タスク、夢・目標への紐づき、日次振り返り、第2領域タスク数、緊急タスク数をアプリ側で集計してからAIへ渡す。
AIは「事実 → 気づき → 来週の重点」に整理するだけで、既存データを変更しない。

理由:

週次レビューは感想文ではなく、「今週、本当に夢に向かって動けたか」を短時間で確認する機能であるため。
AIに全判断を丸投げせず、事実データを先に構造化することで、放置夢や緊急偏り、第2領域の実行状況を安定して扱える。

影響:

- 振り返りタブに週次レビューAIパネルを追加する
- 同一週・同一データではキャッシュを再利用する
- AI提案履歴一覧や自動タスク登録は今回実装しない

## 2026-07-24: 「夢を、今日の行動に変える。」を中核コンセプトにする

判断:

このアプリの中核コンセプトを「夢を、今日の行動に変える。」とする。
今後の機能追加、UI改善、AI設計は、このコンセプトに沿って判断する。

理由:

このアプリは、夢を記録するだけのノートでも、期限順にタスクを並べるだけのToDoでもない。
夢に期限を持たせ、目標へ分解し、今日の行動と振り返りを変えることに価値があるため。

参考思想:

渡邉美樹氏の『夢に日付を！』にある「夢に期限を持たせ、その夢から逆算して今日の行動を変える」という考え方を重要な参考思想のひとつとする。
ただし、特定書籍の文章、表現、構成、名称、図表、ワークシート等は複製せず、デジタル、AI、スマートフォン、現在のユーザー体験に適した独自のプロダクトとして設計する。

AIの位置づけ:

AIはユーザーに代わって夢を決める存在ではない。
AIは、夢と期限から逆算して、今日できる具体的な行動へ落とすための補助役とする。

ホーム画面への影響:

ホームは今日の行動を最優先する。
夢や目標の件数など、行動判断に直接必要ない管理指標をホームの主役にしない。
今日やることが、どの夢、どの目標、いつまでに達成したいことにつながるのかを、必要最小限の情報で伝える。

## 2026-07-24: 6本の柱を夢手帳の土台にする

判断:

夢は「仕事・家庭・健康・趣味・教養・財産」の6本の柱で整理する。
既存の `dreams.category` フィールドを利用し、新しい大きなデータモデル変更は行わない。

理由:

今後、夢を5年、1年、月、週、今日へ逆算する際に、人生全体の偏りを確認できる土台が必要なため。
6本の柱を先に整えることで、仕事だけ、財産だけに偏らず、「夢を、今日の行動に変える。」流れを人生全体で扱いやすくなる。

既存データ互換:

既存の自由カテゴリーは勝手に削除・変更しない。
6本の柱に一致するものはそのまま利用し、一致しないものは表示上「未分類」または近い柱として扱う。

影響:

- 夢入力で6本の柱を選択できる
- 夢一覧で夢、達成日、柱が分かる
- 夢画面内で6本の柱ごとの夢を確認できる
- AIは今後、柱分類や計画分解の補助として扱う

## 2026-07-24: 目標階層を5年 / 1年 / 今月 / 今週 / 今日へ整理する

判断:

目標の基本階層を「5年計画 → 1年目標 → 今月目標 → 今週目標 → 今日の行動」に整理する。
新規入力と通常表示ではこの新階層を使い、旧10年目標・旧3年目標はlegacyとして残す。

理由:

「夢を、今日の行動に変える。」ためには、長期の夢から今日までの逆算ルートが短く自然につながる必要があるため。
5年、1年、月、週、今日の粒度は、スマホで毎日扱う夢手帳として分かりやすく、今後の転記や週次計画にもつなげやすい。

既存データ互換:

既存の `ten_year` / `three_year` は削除・上書きしない。
表示上は旧階層として扱い、編集時に新しい階層へ移せるようにする。

影響:

- `goals.level` の新規候補は `five_year` / `one_year` / `monthly` / `weekly` / `daily`
- `goals.parent_goal_id` で上位目標との関係を持てる
- AIの夢具体化提案も新階層に合わせる
- Supabase利用時は `supabase/schema.sql` の `parent_goal_id` 追加を適用する必要がある

## 2026-07-24: 未完了行動は複製せず同じタスクを転記する

判断:

未完了タスクを次へ送るときは、原則として別タスクを複製せず、同じタスクの期限と状態を更新する。
転記先は短期行動管理に絞り、明日、今週中、来週、今月、日付指定、いったん保留、もうやらないを扱う。

理由:

未完了行動を放置すると、夢から今日の行動への流れが途切れるため。
一方で複製を増やすと同じタスクが散らばり、スマホで毎日扱うには重くなる。
そのため、まずは「終わったら完了、終わらなければ転記」という手帳運用に近い体験を優先する。

履歴:

履歴一覧UIは今回作らない。
内部データとして `reschedule_count` と `reschedule_history` を保持し、将来「何度も転記している行動を見直す」機能へつなげる。

影響:

- タスクの夢・目標紐付けは転記しても維持する
- 完了済み・アーカイブ済みタスクは転記対象にしない
- Supabase利用時は `tasks.reschedule_count` と `tasks.reschedule_history` の追加schemaを適用する必要がある

## 2026-07-25: 夢・目標は削除できるが関連行動は残す

判断:

夢と目標には完全削除操作を用意する。
ただし、夢を削除しても関連する目標・タスクは削除せず、夢との紐付けだけ外す。
目標を削除しても関連するタスク・下位目標は削除せず、目標との紐付けだけ外す。

理由:

実使用では、間違えて入力した夢や目標を消せないことがストレスになるため。
一方で、夢や目標に紐づく行動履歴まで同時に消すと、「夢を、今日の行動に変える。」ために積み上げた記録を失う可能性がある。

影響:

- 夢カードと目標カードに削除ボタンを追加する
- 削除前に確認ダイアログを表示する
- 関連タスクは残し、必要なら後から別の夢・目標へ紐付け直せる
## 2026-08-01: AI中心からデジタル夢手帳中心へ優先順位を変更

判断:

現在の主要方針は、AI機能を前面に出すことではなく、渡邉美樹氏の「夢に日付を！」の思想を参考にしながら、独自のデジタル夢手帳として毎日使える基本体験を整えることとする。

理由:

- 中核コンセプトは「夢を、今日の行動に変える。」であり、AIは主役ではなく逆算と行動化の補助役である
- 夢、達成日、5年、1年、今月、今週、今日、実行、消し込み、未完了の転記、振り返りの流れが継続利用の中心になる
- 紙の手帳で面倒な転記、実行履歴、繰り返し、偏り検出などをデジタルで支援することに価値がある

影響:

- ホームは管理指標ではなく「今日やること」を最優先にする
- 未完了タスクは放置せず、次にいつやるか決め直す
- 繰り返しタスクはタスク本体を消さず、日ごとの実行記録として扱う
- Googleカレンダー連携は外部OAuth設定が必要なため、人間の設定完了後に進める

## 2026-08-01: 逆算構造は既存の親子関係を使って段階的に強化

判断:

「1年 → 今月 → 今週 → 今日」の逆算構造は、新しい大規模テーブルを追加せず、既存の `goals.parent_goal_id` と `tasks.goal_id` を使って実装する。

- 将来、より細かい計画項目が必要になった場合だけ、専用テーブルを検討する

## 2026-08-01: ホーム上部はモチベーションカードと期間カードの横スワイプにする

判断:

ホームでは最上部にユーザー自身が登録したモチベーションカードを表示し、その下に今週・今月・1年後・5年後・10年後・20年後の目標カードを横スクロールで表示する。
今日やることは期間カードの下に独立表示し、期間カードには含めない。
各カードはコンパクトにし、今日の行動判断を邪魔しない補助情報として扱う。

理由:

- 朝開いた瞬間に、なぜ目標へ向かうのかを短く思い出せる
- 今週、今月、1年後、将来の順に見ることで、今日の行動がどの期間目標につながるか確認しやすい
- 1か月後、1年後、将来の目標を縦に並べると、今日の行動が埋もれる
- スマホでは横スワイプのほうが期間ごとの確認を軽くできる
- 今日やることは横スクロールには含めず、ホームで独立表示する

影響:

- ホームの管理指標は増やさない
- 期間カードは一覧ではなく、代表目標と下位項目の短い確認に留める
- 期間カードの進捗バーは表示せず、高さを抑える
- 期間カードをタップすると、その期間の目標へ絞り込んだ目標画面を開く
- 詳細確認や追加は目標画面・タスク画面へ送る
- データ構造は既存の `goals.parent_goal_id` と `tasks.goal_id` を利用し、新しい大規模DB変更は行わない

## 2026-08-01: ユーザー向け概念を目標と実現するためのタスクへ整理

判断:

下部ナビから独立した「夢」画面を外し、日常的に操作する主要概念を「目標」と「実現するためのタスク」へ寄せる。
既存の `dreams` は削除せず、互換用の長期目標データとして残す。

理由:

- ユーザーが「夢か目標か」を毎回考えると入力が重くなる
- 期限を持つ実現したい状態をすべて目標として扱うほうが、20年→10年→5年→1年→今月→今週→今日へ分解しやすい
- 既存 `dreams` / `goals` / `tasks` を一括統合するとデータ消失や誤移行のリスクが高いため、まずUI概念を整理し、内部互換を維持する

影響:

- 下部ナビはホーム、目標、タスク、振り返り、設定へ簡略化する
- `goals.category` を追加し、目標自体が6本の柱を持てるようにする
- 20年後・10年後・5年後・1年後・今月・今週を通常の目標期間とする
- 下位目標とタスクは画面上「実現するためのタスク」として表示する
- 既存AI機能の内部名は残しつつ、新規提案の目標階層は新期間に合わせる

## 2026-08-02: 目標設定はタイトル、達成日、分解タスクを最優先する

判断:

目標設定・編集画面では、最初に「タイトル」「達成日」「達成するためのタスク」を入力できる構成にする。
期間、6本の柱、上位項目、既存データとの関連、メモは詳細設定として下にまとめる。

理由:

- 「夢を、今日の行動に変える。」ためには、まず実現したい状態、期限、そこへ向かう具体項目を決めることが重要
- スマホで毎回すべての属性を入力させると、目標登録が重くなる
- 下位項目は既存の `goals.parent_goal_id` と `tasks.goal_id` を使えば、データ構造を大きく変えずに逆算構造へつなげられる

影響:

- 目標保存時に複数行の下位項目を追加できる
- 今週目標の下位項目は今日やることのタスクとして追加する
- 今月以上の目標の下位項目は次の期間の目標として追加する
- 既存データとの関連は、旧夢データとの紐付けを維持し、既存目標・タスク・メモは検索確認できる形に留める

## 2026-08-05: 毎日開きたくなる夢手帳UXを優先する

判断:

新機能追加よりも、毎朝・毎晩の流れを軽く回せるUXを優先する。
ホームは「モチベーションカード → 今日やること → 期間別目標 → 今日やり遂げたこと」の順にし、AIや管理指標を主役にしない。

理由:

- 中核コンセプトは「夢を、今日の行動に変える。」であり、毎日開いて行動できることが最重要
- 振り返り項目が多いと夜の入力負荷が高くなるため、完了記録と気づきに絞る
- 明日の行動は振り返り内のメモではなく、タスクとして次の日へつなげる
- 「重要・緊急でない」第Ⅱ領域を見える化することで、未来を変える行動を後回しにしにくくする
- モチベーションカードは名言ではなく、目標を達成したい理由を思い出すための補助として扱う

影響:

- 保存成功時は「保存しました」を短時間表示する
- モチベーションカードの画像URL入力は廃止し、端末から画像を登録する
- 目標の達成日はカレンダー選択と手入力の両方に対応する
- AIは既存の分解補助、今日候補、週次レビューの補助役に留める
